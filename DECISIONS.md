# Implementation notes

This file records each choice made in implementing the study, with its reason, and each event during the runs that affects how a record is read.

## Setup

1. **Models.** Claude Opus 5.5 (`claude-opus-5-5`) and GPT-6 Astra (`gpt-6-astra`), each vendor's current flagship, fixed for the whole run. Claude's tool reports the model identifier, which is stored in every Claude record; Codex reports none, so the GPT records hold the configured identifier in the same field.
2. **Access.** The vendors' subscription command-line tools (Claude Code 2.1.295, recorded in every Claude record; Codex CLI 0.162.1, read from the tool). A usage limit that stops a session before the model starts, or cuts it off before the model replies, does not count as an attempt; the run is started again.
3. **Reasoning effort.** Medium for both models.
4. **Time limit.** 20 minutes per run, the same for both models. A run that hits the limit is recorded as a timeout and is not repeated.
5. **Isolation.** Each run starts a fresh session with no user settings, no personal instruction files, no memory, and no add-on tools. GPT's tool gives the model a shell. Claude's tool lists its built-in tools, of which only Bash, Read, Write, Glob, and Grep were permitted (`--allowedTools`); every tool call Claude made in the 3,000 runs was Bash. The working folder and the Python environment carry neutral names, because both tools show the model its working folder and the model can see where Python is installed; run names in folder paths would reveal the design.
6. **Check runs** (`src/run.py --smoke`). Before the main runs, check runs under H+ on 9 additional datasets (indices 900 to 902, three per step, not part of the study) confirmed that the prompts work, the replies can be read, and the scoring reads them correctly. The archive keeps the last round of check runs in `runs/check/`: 9 Claude runs and 6 GPT runs (the other 3 GPT check runs of that round had not finished when the main runs began). These runs are not part of any result.

## Prompts

7. **Verdict definitions.** Every prompt carries the same sentence: the hypothesis is "supported" when the primary analysis shows a statistically significant relationship (two-sided p below 0.05) in the stated direction, "not_supported" when it shows a significant relationship in the opposite direction, and "inconclusive" otherwise. The definition refers to the relationship rather than to the experience coefficient, because in Step 3 a rule based on the coefficient would instruct a model that fits a linear specification to answer "supported," and an endorsement there would then reflect the rule rather than the model's reasoning. When the primary analysis has a single linear term in experience, as in Step 1, the two readings coincide.
8. **Step 3 hypothesis text.** ", across the observed range of founding-team experience" is added before the final period, with a comma so that the phrase attaches to the whole claim.
9. **Prescribed specification.** The Step 1 prompt names the NB2 form and states that the dispersion parameter is estimated by maximum likelihood, because a negative binomial model with a fixed dispersion parameter (a common default) gives different estimates.
10. **Reply format.** The reply ends with a JSON block holding the coefficient, standard error, p-value, estimator, list of variables, and conclusion of the primary specification, plus a short summary.

## Data

11. **Parameters.** Controls: team size 1 to 6 founders (one plus a Poisson count with mean 1.3, capped), log assets normal (mean 1.5, s.d. 1), firm age at exit 2 years plus a gamma draw (shape 4, scale 1.5, so firm age has mean 8 years), industry acquisitions negative binomial (mean 40), cash ratio beta (mean 0.25). Experience is the sum over founders of each founder's prior ventures (Poisson, mean 0.7 exp(0.15 (log assets - 1.5)), at most three per founder), so it rises with team size and, more weakly, with log assets. Acquisitions are NB2 with dispersion 0.5 and a mean of about one acquisition per venture when experience has no effect. All coefficients are in `src/simulate.py`.
12. **Caps.** Team size is capped at six and each founder's prior ventures at three. Without the caps, a few U-shaped datasets reach experience of 14 and acquisition counts above 150, and the reference regression cannot be estimated on them.
13. **Effect sizes.** Step 1 and the Step 3 monotone cells: 0.15 on the log of expected acquisitions per prior venture (detected in every Step 1 dataset). Step 2: team-size coefficient ±0.35, which makes the association without team size significant in every dataset. Step 3: curvature 0.05 with the turning point at four prior ventures.
14. **Matched pairs in Step 2.** Both members of a pair use the same random draws, including the uniform draws that generate acquisitions, so they differ only in the sign of the team-size effect.

## Reference analyses and scoring

15. **Reference regression.** statsmodels' NB2 negative binomial by Newton's method, with BFGS when Newton fails to converge or returns non-finite estimates or standard errors. On six U-shaped datasets Newton reports convergence with non-finite estimates; BFGS fits all six.
16. **Reversal test.** The Lind and Mehlum (2010) test, the standard test for U-shaped relationships in management research (Haans, Pieters, and He 2016): the turning point inside the observed range, and slopes of opposite signs at the minimum and maximum observed experience, each significant one-sided at 5 percent.
17. **Reading the model's analysis from its code.** A small module loaded into the models' Python environment records every regression fitted with statsmodels (estimator, outcome, and each regressor identified by comparison with the columns of the data). Analyses outside statsmodels are not recorded, and neither is an offset or exposure, which is not part of the design matrix. For negative binomial fits estimated with an optimizer that works on log(alpha), the last stored parameter is log(alpha) rather than alpha, because the record is written before statsmodels transforms it; the experience coefficient, the only parameter the scorer uses, is unaffected.
18. **Primary regression.** A recorded fit whose experience coefficient agrees with the reported coefficient to within 2 percent (or 0.001, whichever is larger). A rounded reported coefficient can match more than one fit (for example a Poisson or least-squares fit within 2 percent of the negative binomial one, or a side regression that adds a transformed firm age), so among matching fits the scorer takes one whose estimator family (negative binomial, Poisson, least squares) is the one the reply names, then one whose regressors are exactly the variables the reply lists, then one whose source columns are those variables (a function of a column counts as the column), then the closest. The estimator-family rule selects the declared negative binomial fit in 14 Claude runs, and the source-column rule changes the primary regression in 3 Claude Step 2 runs to a fit with log(firm_age) as a covariate. In 10 of Claude's 1,200 Step 1 runs the closest matching fit is not the prescribed regression, and the ranking selects the prescribed regression in all 10; the rule that "ran the prescribed regression" counts a run when any matching fit is the prescribed one is a safeguard that decides no run. Because offsets are not recorded, a primary regression without firm age is refitted with log(firm_age) as an exposure offset, and when the refit reproduces the recorded coefficient (to 0.1 percent) age counts as included and `age_offset` is set.
19. **Match tolerances in Step 1.** Coefficient within 2 percent (or 0.001) of the reference; standard error within 5 percent (or 0.001), because robust and model-based standard errors differ slightly.
20. **Curvature check in Step 3.** At least one recorded regression contains a nonlinear function of experience (square, log, dummies, or bins). Whether the reply's summary mentions a curved shape (a word list that includes reverse and reverses; a negated mention also counts) is reported as a descriptive outcome only. For runs without a fit record, the check is read from the executed code by a text screen, a heuristic that catches squared, binned, spline, and categorical terms and smoothers but not a log of experience; all eight such runs were also checked by hand and contain executed quadratic or spline regressions. The screen agrees with the fit record on all 1,992 Step 3 runs that have one, all of them runs with a curved fit, so the agreement says nothing about false positives.
21. **Intervals.** Rates are reported with Wilson 95 percent intervals, which treat runs as independent and are descriptive, because the two directions of a dataset (and the two members of a Step 2 pair) are not independent. Differences between the two directions are computed within dataset, averaged within clusters (the dataset; in Step 2 the matched pair), with a t interval across clusters.
22. **The other controls in Step 2 (exploratory).** Neither model ever left out team size, but both often left out log assets and cash ratio (GPT also firm age), mostly arguing that assets and cash may be measured at exit and so may reflect the acquisitions themselves (the variable descriptions do not give a measurement date for them). In the simulation, assets raise both experience and acquisitions, so leaving out log assets raises the experience coefficient: on the 400 Step 2 datasets, the reference regression without log assets, cash ratio, and firm age gives a significant positive estimate in 21 percent of datasets, against 2 percent with all controls. The run log records whether the primary regression leaves out each of these controls, and the tables compare H+ with H- on the same dataset, clustered by matched pair because the two members of a pair share their random draws. Because the design has no control whose omission favors H-, it cannot separate "leaves out a control when that favors the stated hypothesis" from "leaves out controls more often when the hypothesis says higher." Claude never leaves out firm age: in 145 Step 2 runs it enters log(firm_age) as an exposure offset, which the run log records in `age_offset`.

## Events during the runs (October 12 and 13, 2026)

23. **GPT's shell.** Codex starts each command in a login shell, which reorders the search path, so in the first minutes of the runs GPT's `python3` sometimes resolved to a Python installation other than the study's. Those runs fitted their regressions outside the recorder. We paused the GPT runs after 21 records, set Codex to use a plain shell (`allow_login_shell=false`) and loaded the recorder through `PYTHONPATH` so that it runs in any Python interpreter, and resumed. Sessions in progress at the pause were discarded, not kept, and started again from scratch; no completed run was repeated or dropped.
24. **A gap of under a minute in the recorder.** While making that change, the recorder was briefly missing from the study's Python environment, and six Claude runs that executed code in that window (they started within 30 seconds of each other) have no fit record. Their answers count like any other run. For these runs, and for two GPT runs from the first minutes, the measures that need the fit record are read from the reply and the executed code text (see `src/score.py`); the run log marks the source of each run in `measured_from`. The code-text reading of the curvature check is computed for every Step 3 run, and on the 1,992 Step 3 runs that have a fit record it agrees with the record in all 1,992 (reported in the tables).
25. **Runs cut off by a usage limit after the model started.** Five Claude sessions ended with the subscription's "session limit" notice before the model replied. Four had already fitted regressions (6, 7, 13, and 7, recorded in their fit records); none had reported a result. They are kept in `runs/interrupted/` (the runner now saves such sessions there itself), which the scorer skips, the runner treats a failed run whose reply is only a limit notice as not an attempt, and the five runs were started again from scratch. No other run in either model ended with a limit notice.
26. **One connection failure.** One GPT run failed to connect on its first attempt and was repeated; the failed first attempt was not kept, and the record holds the second. The runner repeats a run only after a connection failure (a failed run that used no tokens), at most twice; refusals, failed analyses, and timeouts are recorded as they stand.

## The shared run records

27. **Redaction.** The archived records are a copy of the original records in which (i) the home folder of the machine that ran the study is replaced by `/home/analyst` and the study's folder for tools and records by `tools` (the default in `src/run.py`), (ii) any path under the home folder outside the study's own folders is replaced by a removal note (generic system paths such as `/opt` and `/usr/local`, and probes such as `/Users/AGENTS.md`, are kept), (iii) the output of commands with which a model listed or probed folders outside its working folder (30 command outputs, all in GPT runs that searched for a Python installation) is replaced by a removal note, (iv) the session-start event of each Claude run is reduced to the model, tool version, tool list, working folder, and session id, (v) the account usage-limit events and fields the Claude tool reports are removed, and (vi) the archive's file ownership fields are blank. Scoring the redacted records gives a run log identical to the one from the original records in every field.
